# P2–P3 — 재개 가능한 수집과 10초 기준 결과

- **날짜:** 2026-11-01 (Asia/Seoul).
- **관련 요구:** F1–F11, N1–N7.
- **범위:** 1만 후보 체크포인트, 고정 목표 60개, MSE 검색, 실제 사진 캐시와 무음 MP4. 추가 소스·회전 검색·원본 오디오·10만 이상 수집은 후속 범위다.

## 구현과 판단

P1의 `SceneReader`, 품질 판정, 좌표 계산을 재사용했다. `collection/`에는 전역 창 배정·블록 수집·저장을, `matching/`에는 목표 추출·검색·출력을 묶었다. 공통 명암 특징은 `features.py`에 둔다. uv 의존성에 Parquet의 PyArrow, 자원 계측의 psutil, 구간 디코드의 PyAV를 추가했다.

### 수집과 재개

- 12개 AOI를 6개 지형군에 나누고 총 후보 수를 균등하게 배분한다. 공간 기준은 후보 중심의 AOI/촬영 footprint 포함이다. 원본 픽셀 원점에 고정한 창을 50% stride로 생성해 각 창을 한 읽기 블록에만 배정하고 필요한 오른쪽·아래 경계 영역을 포함한다.
- AOI당 카탈로그 검사 상한은 100 items, 장면은 서로 다른 MGRS 공간 최대 3개다. 같은 공간의 여러 촬영 날짜를 다른 지형으로 늘리지 않는다. 장면 목록과 블록 계획은 고정 파일로 보존한다.
- 기본은 장면 동시성 1, 2048px 블록과 256/512/1024px 폭이다. 실제 창 높이는 1444:1080 비율에서 유도한다. 신규 블록 계획은 축소 SCL로 유효 지형이 많은 부분을 먼저 읽되 최종 후보 품질은 원본 격자에서 판단한다. 최초 실행 때 이미 저장한 계획은 유지했다.
- 유효 RGB mask·SCL 결함·구름 판정은 P1 규칙을 따른다. 정상적인 단색 지형을 삭제하지 않는다. 인접한 같은 스케일의 유사 후보는 dHash와 coarse 명암 차이를 함께 확인해 `near_duplicate_of`로 연결하고 보관한다. 실제 후보 수를 고유 형태 수로 보고하지 않는다.
- 장면·스케일 균등 배분을 우선하고, 할당이 부족하면 이미 읽은 블록의 남은 유효 창을 먼저 쓴다. 남은 AOI 수량은 다른 유효 스케일에 재배분할 수 있다. 특정 스케일의 엄격한 비율을 맞추기 위해 불필요한 픽셀 요청을 계속하지 않는다.
- 완료 후보의 RGB 전체를 저장하지 않는다. 공통 크기 256×191 RGB에서 16×12·32×24 uint8 명암을 만들고 출처와 함께 불변 Parquet/NumPy shard로 저장한다. 보고 표본으로 선택된 후보의 RGB를 함께 보관하고 최종 비교 시트는 결정적 무작위 200개로 만든다. 불변 shard에는 수집 중 교체된 표본도 남을 수 있다. 후속 최종 선택 사진은 별도 캐시에 남긴다.
- SQLite는 작업 cursor·상태·타일 행 검색을 관리한다. staging의 배치 파일을 닫고 최종 shard 디렉터리로 rename한 뒤 manifest를 교체하고 SQLite를 갱신한다. 공개 직후 중단되어 manifest/SQLite가 뒤처지면 최종 shard에서 복구한다. 미공개 staging은 검색에서 무시한다.
- 단일 writer OS 잠금을 사용한다. 프로세스 종료 후 다음 writer가 잠금을 얻으면 남은 RUNNING을 PENDING으로 회수한다. quota 때문에 창이 남은 블록은 압축 캐시에 유지하므로 재개 시 같은 픽셀을 다시 받지 않는다. 완료 목표로 재실행하면 네트워크에 접근하지 않는다.
- RAM·디스크·여유 공간 상한과 블록 시도 횟수를 둔다. 자원 한도만 바꿀 때는 기존 인덱스 namespace와 데이터는 유지한다. 소스·AOI·추출 설정은 기존 인덱스와 혼합하지 않는다. 정상 수신한 자료를 재검증하려고 다시 다운로드하지 않았다.

첫 수집은 7,815개에서 부분 완료했다. 부족분은 주로 엄격한 스케일 균등 할당과 AOI 경계 장면의 낮은 유효율 때문이었다. 부족한 수량을 성공으로 표시하지 않았으며, 기존 인덱스와 블록 캐시를 보존한 채 재개해 남은 유효 창을 사용했다. 장면 첫 순서에 재개할 때마다 추가 할당이 쏠리지 않도록 기본 장면 한도도 고정했다.

### 목표 추출·검색·출력

- 로컬 MP4의 38–48초를 6fps 목표 60개로 고정했다. PyAV가 필요한 구간만 디코드하고, Fraction으로 목표 시각과 실제 PTS를 비교해 가장 가까운 프레임을 고른다. 동률이면 이전 프레임이다. 입력 checksum, crop, 목표 시각, 선택 PTS/time base를 보관한다.
- 타깃과 후보는 같은 Pillow RGB→L/BOX 경로를 사용한다. 강제 이진화·명암 정규화·실루엣 합성은 하지 않았다. 현재 지원 입력은 회전 없는 SAR 1:1이며 다른 회전/픽셀 비율은 명시적 오류로 남긴다.
- coarse 픽셀은 int32로 확장해 정확한 SSE를 계산하고 `차원수 × 255²`로 나누어 `[0,1]` MSE로 보고한다. uint8 overflow와 가까운 후보의 float32 상쇄를 피한다. 후보 배치와 타깃별 Top-20만 유지하고 동률은 tile ID 순서로 정한다.
- 검색 run은 실제 읽은 shard 목록을 고정한다. 결과의 모든 순위에 run/target/tile/scene/shard/feature row·위치·촬영일·추출 창·점수를 남긴다.
- `materialize`는 기존 표본 PNG와 블록 캐시를 우선 사용한다. 최종 선택과 고정 평가 목표 20개의 Top-5에 필요한 사진만 준비하며, 없는 사진만 실제 원본에서 읽는다. 선택 실패는 차순위와 사유를 기록한다.
- 렌더는 매칭 사진을 6fps 슬롯에 유지해 24fps로 인코딩한다. 원래 컬러, 흑백, 좌측 원본/우측 실제 사진 비교를 별도 MP4로 만든다. 256×191 기본 사진의 하단에 1px만 패딩해 yuv420p의 짝수 크기를 맞춘다. 사진 사이의 보간·합성·crossfade는 없다.
- 사용권 미확인 상태이므로 원본 음원 경로는 구현하지 않고 명시적 무음 모드만 제공한다. 공개 업로드는 하지 않는다. 촬영 연도별 Sentinel 출처 고지와 선택 사진 checksum을 기록한다.

## 실행 방법과 제한된 확인

실제 명령은 README에 유지한다. 이번 실행 경로는 다음과 같다.

```text
uv run badapple-earth collect --config config/collect.json --output data/index/p2-10k --limit 10000
uv run badapple-earth targets --config config/targets.json --output data/targets/38s-10s-6fps
uv run badapple-earth match --targets data/targets/38s-10s-6fps --index data/index/p2-10k --output data/runs/p3-10k --top-k 20
uv run badapple-earth materialize --targets data/targets/38s-10s-6fps --index data/index/p2-10k --run data/runs/p3-10k
uv run badapple-earth render --targets data/targets/38s-10s-6fps --run data/runs/p3-10k
```

변경한 저장·검색 계약의 오프라인 테스트 6개가 통과했다. 블록 경계의 누락/중복, 공통 특징, 공개 직후 장애 복구, 캐시 재개/증분 수집, PTS 동률, uint8 극값·Top-K 동률을 확인했다. 합성 데이터는 이 테스트에서만 사용했다. 기본 전체 테스트나 기존 수신 데이터의 네트워크 재검증은 수행하지 않았다.

수집 중 Windows가 실행 중인 CLI 파일을 잠가 uv의 프로젝트 재설치가 한 차례 실패했다. 실행 종료 후 `uv sync --locked`가 정상 완료했고, 의존성과 lockfile은 일치하는 상태로 이어갔다.

## 해석과 다음 단계

이 결과는 작은 후보 집합에서의 기술 기준선이다. 다운로드 성공·검색 점수·파일 생성·정지 비교·실제 재생 평가는 구분해서 기록한다. 소규모의 낮은 시각 품질을 방식 전체의 실패나 확대 중단 근거로 해석하지 않는다. P4는 같은 목표 세트·metric을 유지하며 가용 범위에서 공간·스케일·후보를 확대하는 단계다.

HTTP 요청 수와 실제 수신 바이트는 계측하지 않았다. 저장된 블록 크기나 픽셀 수를 네트워크 실측값으로 바꾸어 보고하지 않는다. 메모리 수치는 블록 경계에서 관측한 RSS이며 모든 순간의 최고치를 보장하지 않는다.
